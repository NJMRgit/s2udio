## SVP4 integration — fixed mpv IPC socket (host, 2026-08-11)

Goal: make s2udio play nice with SVP4 (SmoothVideo Project 4, installed at
`~/.local/bin/SVP4`, manager running). SVP4 drives mpv over the JSON IPC
socket `--input-ipc-server=/tmp/mpvsocket` (its `setup/mpv` setting).

Root cause of "SVP not working from s2udio": `scripts/mpvSockets.lua`
(installed to `~/.config/mpv/scripts/`) overrides `input-ipc-server` at
runtime — mpv binds `/tmp/mpvsocket` at init, then the script swaps the
socket to `/tmp/mpvSockets/<pid>`, leaving a **dead** `/tmp/mpvsocket`
file. SVPManager connected → connection refused → no interpolation; s2udio
meanwhile tracked playback over the *other* (per-instance) socket. Two
sockets for one mpv, one of them lying.

Changes (this session):

- **src/core/mpv.rs** — `MPV_SOCKET` is now `/tmp/mpvsocket`; `run_mpv_playlist`
  passes `--input-ipc-server=/tmp/mpvsocket` explicitly; `mpv_socket()`
  discovery order: live fixed socket → newest `/tmp/mpvSockets/<pid>`
  (legacy) → stale fixed path (caller detects dead). Added
  `mpv_socket_in()` (+4 unit tests, 14/14 mpv tests green).
- **scripts/s2u-mpv-tracker** — same discovery order (`_socket_live()` +
  fixed-first); installed to `~/.local/bin`.
- **scripts/mpvSockets.lua deleted** (repo + `~/.config/mpv/scripts/`) and
  every installer/gate/doc updated (setup.sh, flake.nix, container deploys,
  G1/G8 gates, test-setup-distro, arch-baseline fixture, HANDOFF,
  mpv-session/distro-support/mpris-validation docs).
- mpv.conf keeps `input-ipc-server=/tmp/mpvsocket` (the user's line — SVP's
  contract). `~/.local/bin/s2udio` re-installed (rename-over-busy, running
  instance keeps old inode until restarted).

Verified headless: mpv launched with the flag → `/tmp/mpvsocket` live for
the whole session (15× 1s state polls), SVPManager log shows
`mpv v0.41.0 via /tmp/mpvsocket` + `playing at 50 [25 *2/1]` (RIFE),
no crash in the window.

Known SVP-side issue (out of scope, user-directed): with the RIFE engine
the bundled `libvstrt.so` is built against TensorRT 10.13.2 but loads
10.13.3 (`vstrt: TensorRT version mismatch … fingers crossed`) and mpv
SIGSEGVs ~30 s in (`vsTrtGetFrame` in `libvstrt.so`). System TRT is
11.1 (so.11) and not what SVP loads. Mitigations to try: use the
SVPflow (non-RIFE) engine, or align SVP's TensorRT bundle.

## SVP4 crash root-caused: RIFE/TensorRT engine on 4K (host, 2026-08-11)

After the toggle + SVP-mpv changes, mpv again froze and closed ~20-25 s into
4K playback (coredumps 13:29 / 13:31 — now in SVP's own mpv). Backtrace:
`libsvpflow2.so VectorField::zeroVectors -> SmoothFpsCore::calculate` —
IDENTICAL on the distro VapourSynth 77 AND SVP's bundled VS R73, so the VS
version was never the culprit. The real common factor: the **RIFE engine**
(the `vstrt: TensorRT version mismatch` warning — SVP's bundle ships
libnvinfer 10.13.3 while libvstrt.so was built against 10.13.2; on 4K the
SmoothFps_RIFE vector-field blending writes OOB and segfaults). All crashing
sessions were 4K <60fps with the "RIFE AI engine" profile; 1080p and
HFR-ignored (60fps) sessions were fine.

Fix: keep the winning profile but switch its engine to **SVPflow**
(`profiles.cfg` `P04a171d5.../rife: false`; backup at
`profiles.cfg.bak-rife-on`). Verified: The Beekeeper 4K HEVC 10-bit
(BT.2020 PQ) 23.976fps, 180 s continuous interpolation
(`playing at 47.952 [23.976 *2/1] /10 bit`), no crash, no TRT warnings.
Re-enabling RIFE in the SVP UI brings the 4K crash back; the proper fix is

## s2udio "won't launch / no UI" — thumbfast leftover holding /tmp/mpvsocket (host, 2026-08-11)

Symptom: s2udio starts ("Application initialized successfully") but the UI
never draws; process stays alive; instances die after a while. Reproduced
in tmux (the G10-style capture-pane check): my binary drew nothing while a
stashed/pristine build drew the full TUI — a real regression.

Root cause: a **thumbfast thumbnailer subprocess** (spawned by my Beekeeper
test mpv at 13:36, `--scripts=/tmp/thumbfast505487.run` chain of mpv →
bash → tail) **inherited the parent mpv's `/tmp/mpvsocket` LISTEN fd** and
lingered for hours, never accepting. s2udio's new `mpv_socket()` discovery
did a plain blocking `UnixStream::connect()` to `/tmp/mpvsocket` — with the
stuck listener's backlog full, the event loop's first mpv poll blocked
forever → no render, no input handling. The pristine discovery never
connected at startup, so it was unaffected (the bisect pointed straight at
`src/core/mpv.rs`).

Fix (`src/core/mpv.rs`):
- `connect_socket(path, timeout)`: nonblocking connect (libc
  `SOCK_NONBLOCK`) → `EINPROGRESS` → `poll(POLLOUT, timeout)` →
  `SO_ERROR`; **`EAGAIN` (backlog full) fails immediately**. Used by both
  `mpv_socket()`'s `is_live_socket()` and every `mpv_exchange()` call —
  a stuck/dead socket can now never hang the app (300 ms budget).
- Regression test `connect_socket_times_out_on_a_stuck_listener`
  (libc listener with `listen(fd, 0)` + one pending connection fills the
  single slot; the next connect must error fast). 15/15 core::mpv tests,
  1343 total (the 2 pre-existing host failures unchanged).
- Installed; tmux render check back to 4738 chars (full Queue tab).

Housekeeping: killed the hung thumbfast chain (506086/506093/506095),
removed the stale `/tmp/mpvsocket` and dead `/tmp/s2u-*.sock` files.
