**Changed** (all committed host-side on `working`):

1. **Popup labels** (`src/ui/modals/paste.rs`): single-file actions are

## Round 20 — torrent popup UI polish + duplicate-paste fix (container)

Feedback: [FEEDBACK-2026-08-09-15.md](../../../FEEDBACK-2026-08-09-15.md)
(pulled at `e195764`, "round 20 feedback filed"). Round 19 (config
separation) is implemented host-side and stays uncommitted in the host's
testing checkout — not touched here. All changes below are in the
container checkout on `working`, uncommitted, for the host to validate
after the pull.

**Changed:**

1. **Wait window — DL-speed row removed** (`src/ui/modals/paste.rs`):
   the `[Torrent]` scan-pending branch now renders only
   `Loading <label>… mm:ss` + `esc to cancel` (+ `Cancel`). The
   `DL <speed> · need ≥ <min> KB/s ✓/✗` header row and the
   `scan_wait_speed` helper are gone (live use showed the row is noise
   during the metainfo wait — speed is ~0 so it always read ✗).
   `TorrentScanProgress.download_speed_kbps` is **kept** in the
   event/`Ctx` structures (the M3 bandwidth gate still reads it); only
   the rendering dropped it.

2. **File picker buttons — Play / Download & Play / Cancel**
   (`src/ui/modals/torrent_file_picker.rs` + `paste.rs`):
   - `TorrentFilePicker` gained a `TorrentPickerAction` (`Play` /
     `DownloadAndPlay`) argument on the confirm callback; the button row
     is now `Play` · `Download & Play` · `Cancel` (button 0 / 1 / 2).
   - `open_torrent_file_picker` passes the action through: `Downloads &
     Play` routes `AppEvent::TorrentScannedPlay { download: true }` →
     the existing "Play and Download" machinery in `start_torrent_playback`
     (engine download job + move to `~/Downloads/s2udio-downloads`).
   - The round-18 fix is preserved: the picker **captures the scan when
     it opens** (now a clone, see below) — both buttons play from the
     captured scan, no re-lookup.

3. **Duplicate-paste bug** (paste same magnet twice → error / won't
   load on the repeat):
   - **Canonical scan keys**: magnets are keyed by their **full
     infohash** (`magnet_infohash_full`, lowercased) in
     `torrent_item_key` and `TorrentItem::source_key` (they must agree —
     the work thread reports scan results under `source_key`), so the
     same torrent pasted twice — even via a different magnet URI (extra
     trackers) — reuses one scan slot. `parse_paste`'s in-paste magnet
     dedupe also uses the full infohash now.
   - **Engine sharing via `Arc`**: `TorrentScan.engine` is
     `Arc<TorrentEngine>`; `Ctx.torrent_engine` is
     `Option<Arc<TorrentEngine>>`. Playback clones the Arc (the scan map
     keeps its own clone), so the engine survives playback and stays
     reusable.
   - **Landed scans survive the popup**: the paste popup's close hook
     no longer clears `Ctx.torrent_scans` — it keeps `Ok` scans (engine
     alive for reuse) and drops `Err` scans (re-paste retries cleanly).
     `play_scanned_or_fresh` and the picker no longer consume the scan
     (they clone it into the event).
   - **Fresh `PlayTorrent` fallback** registers a single-file scan under
     the item's canonical key (`WorkDone::TorrentStreamPrepared` gained a
     `key` field) so a re-paste of a fallback-played torrent also reuses
     the engine.
   - Root cause per host analysis: re-adding the same magnet while the
     first engine is still alive spawned a second rqbit against the same
     `cache_dir` (file/port conflicts, or the scan result for the same
     key being overwritten). With reuse, no second engine is ever
     spawned for the same torrent. (Real-engine smoke in the container:
     adding the same `.torrent` to a fresh engine with existing partial
     cache files returns 200 and the torrent goes `live` — the
     clean-rescan path is sound; the bug was the *concurrent* second
     engine.)
