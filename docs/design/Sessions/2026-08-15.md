  legacy `/ui` path 404s); same random basic-auth token as every other

### Round 42 follow-up — the web UI 401 (2026-08-15, later session)

**User report**: the rqbit web UI showed **401 unauthorized**.

**Root cause (diagnosed + verified with headless Chromium)**:
`web_url()` used `http://s2u:<token>@127.0.0.1:<port>/web/` (URL
userinfo). Chromium replays those credentials for the initial page load
and plain subresources (favicon), but **the SPA's `fetch()` API calls do
NOT carry them** — the requests never even reach the server (controlled
basic-auth test: page 200, `fetch('/data')` never arrives, promise
hangs; rqbit UI showed "Error refreshing torrents network error").
Works with curl (explicit header), not with browser SPAs.

**Fix**: `src/core/torrent_proxy.rs` (new, std-only) — a tiny loopback
reverse proxy per engine that injects the `Authorization: Basic …`
header into every forwarded request and forces `Connection: close` (one
engine connection per request, response framed by socket close — no
body parsing, uploads/SSE pass through). `start_engine` spawns it after
readiness (non-fatal; `web_url()` falls back to the userinfo URL).
`web_url()` now returns `http://127.0.0.1:<proxy port>/web/` — no
credentials in the address bar; the engine port keeps its auth
(defense in depth intact).

**Bug found while testing**: the first `rewrite_head` compared header
names with wrong slice lengths (`get(..14)` vs "authorization" (13),
`get(..12)` vs "connection" (10)) — the `Connection: close` rewrite
never fired, the engine kept connections alive, and the proxy's relay
threads blocked forever (headless Chromium hung through the proxy; also
apparently helped freeze the host PC mid-test — the user rebooted).
Fixed to `get(..13)` / `get(..10)` / `get(..19)`.

**Validation**: unit tests `web_ui_proxy_injects_auth_and_reaches_the_engine`
(fake rqbit: proxied requests carry auth) and
`web_ui_proxy_serves_the_real_rqbit_web_ui_without_credentials` (real
rqbit, skipped when not on PATH). Full e2e with a standalone build of
the exact proxy module: real rqbit (auth on) → proxy → headless
Chromium loads the SPA with live stats and NO error banner, while the
engine's own `/stats` still 401s without credentials. Full suite
**1447/1447 pass minus the 2 pre-existing env failures**; release
rebuilt + reinstalled (md5-verified). The user's running s2udio is
still the pre-fix binary — a restart picks up the fix.

### Round 43 — `s2udio rq start|stop|open` + `s2rq` aliases

**User request**: CLI commands `s2udio rq start|stop|open` plus personal
aliases `s2rq start/stop/open`.

**Design** (`src/core/rqctl.rs`, clap subcommand `Command::Rq`):
- The standalone engine must survive the CLI process, so `rq start`
  spawns a **detached daemon** (hidden `s2udio rq serve` subcommand; new
  process group via `process_group(0)`, SIGTERM/SIGINT signal handler
  with an `AtomicBool` shutdown loop, SIGPIPE ignored). The daemon owns
  the rqbit child + the auth-injecting proxy, registers itself, prints a
  `READY` line (parent reads it over a pipe with a 15 s timeout), and
  self-heals: if rqbit dies it exits and clears the registration.
- **Shared registration** `~/.cache/s2udio/rqbit.json` (`{pid, web_url,
  cache_dir, started_at}`, JSON): the Settings panel's web-UI rows
  reuse/register/liveness-check through it, so the GUI and the CLI never
  run two standalone engines (`rq stop` stops a GUI-started engine and
  vice versa; `web ui` in Settings reuses a CLI-started engine).
- `rq stop` = SIGTERM → poll 2 s → SIGKILL the registered pid +
  unregister; `rq open` = xdg-open the registered URL.
- CLI engine config = config.ron `torrent` section + the state.ron socks
  override (same rule as app startup).

**Pitfalls hit**: (1) `TorrentEngine::Drop` kills the rqbit child — a
CLI `start` that kept the engine in a local dropped it at exit (first
smoke test showed the engine die immediately); the daemon owns it
instead. (2) clap `rename_all = "lower"` maps the hidden `Serve` variant
to `serve` — spawning `__serve` failed with "unrecognized subcommand".
(3) `kill(-1, 0)` signals ALL processes (returns 0 for root), so a
"dead pid" test must use a real out-of-range pid, not `u32::MAX`.

**Validation**: cli parse test (`rq start|stop|open`), 3 rqctl unit
tests (state round-trip, pid liveness, no-state stop is a no-op — made
safe so it never deletes a live registration). Full suite **1451/1451
minus 2 pre-existing env failures**. Live-verified end-to-end with the
installed binary and the fish alias: start (daemon alive, web UI 200
through the proxy, idempotent second start), open (exit 0), stop (daemon
+ rqbit gone, state removed), stop/open without engine (clean errors,
exit 1), rqbit crash → daemon self-heal + unregister.

**Alias**: `alias s2rq 's2udio rq'` appended to
`~/.config/fish/config.fish` (user shell is fish); verified with
`fish -c 's2rq start'` etc.

**Follow-up — `s2udio rq check`** (asked "how do I test the proxy?"): a
`check` subcommand that probes the running engine end-to-end and prints
one PASS/FAIL line per probe — (1) web UI via the proxy without
credentials → 200, (2) API via the proxy without credentials → 200,
(3) the ENGINE port without credentials → 401 (auth intact; the proxy is
the only way in without the token). The registration file gained an
`engine_port` field (`#[serde(default)]`, so old registrations still
parse; a 0 port makes probe 3 fail with a "restart the engine" hint).
Live-verified: 3/3 PASS with the installed binary; clean error (exit 1)
when no engine runs. The user also asked for a README section — added
`## rqbit — torrent web UI & commands` to `README.md` (start/stop/open/
check usage, proxy + auth split, VPN/SOCKS config, `s2rq` alias).
