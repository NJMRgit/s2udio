# Session 2026-08-05

## Work done

### Playlists are audio-only / video-only

- The queue's context menu *Save queue as playlist* became **Create audio
  playlist**: it saves only the **visible** queue rows, so the hidden
  "play without adding to queue" temp entry (and radio/Jellyfin temp
  streams) can never leak into a playlist. *Add queue to playlist* and
  the `s`-key save flow already used the visible set — verified.
- The video queue's context menu gained **Create video playlist** (hidden
  while a Jellyfin item plays — Jellyfin video is not eligible). The
  entries' URLs (stable original links + real titles) are saved into a
  new MPD stored playlist; `MpdClientExt::create_playlist` now prefixes
  absolute paths with `file://` (matching `add_to_playlist_multiple`).
- The Playlists tab shows each playlist's type as a prefix — `♪ ` audio,
  `▶  ` video — classified by a background `PLAYLIST_KINDS` query (first
  entry via `listplaylistinfo 0:1`, MPD >= 0.24, full fetch otherwise;
  any video file/URL marks the playlist video).

### YouTube streams are visible queue content

- `QueuePane::local_queue` filtered out **every** stream URL, so the
  paste popup's Add/Append of a YouTube link put the resolved stream in
  the MPD queue but invisible in the list — "nothing happened, nothing
  plays". The filter now hides only streams that are **not** queue
  content: radio/Jellyfin temp streams (never cached) and the temp-play
  entry. A resolved stream (keyed in the `yt-info` cache) stays visible,
  and its row renders the cached title/channel via `stream_column_line`
  (title in Title + Album, channel in Artist — matching the MPRIS tags).
- `is_audio_extension`/`is_video_extension` strip `?`/`#` so
  `…/movie.mp4?x=1`-style URLs classify correctly (also fixes the paste
  popup accepting those URLs at all).

### One video-style info box (no more drift)

- The queue tab's lyrics box showed the video-style layout for an mpv
  video but the **generic song preview** for the same stream played as
  audio through MPD — and the Playlists tab's info box had a third,
  raw version. Root cause of the repeated "regressed again" cycle:
  the layout existed in three places.
- New `paste::current_yt_info` (mpv video first, else the current MPD
  song's cached stream info) routes audio-stream playback to
  `LyricsPane::render_mpv_info` (time falls back to the MPD status, the
  marquee/scroll key to the queue song).
- The channel/subs + wrapped-description body is now built once by
  `lyrics::yt_stream_info_parts` and shared by the queue box and the
  Playlists tab's info box for selected stream entries.

### The radio playlist is exclusive

- `MpdClientExt::picker_playlists(radio_playlist)` filters the radio
  favourites playlist out of every user-facing playlist picker: queue
  *Add queue to playlist*, playlists song menu, directories, browser,
  search (Add all / Add), and the `s`-key save/delete modals. Songs can
  no longer be added to it; only the Radio tab writes it.

### Playlists tab info box is scrollable

- Added scroll state (`info_state`/`info_area`/`info_items_len`/
  `info_key`/`info_scrollbar_area`), reset when the shown item changes.
- The themed scrollbar (`as_styled_scrollbar`, no `.orientation()` —
  it resets the symbols) appears when the content overflows, exactly
  like the other info boxes.
- Mouse: the wheel scrolls the box, click/drag on the scrollbar jumps
  proportionally (`y * max / height`, bottom pixel →
  `(height-1) * max / height`).

## Decisions

- Playlist entries keep the **resolved stream URL** as-is (MPD can play
  it); display uses the persistent yt cache. Known limitation: the
  signed URLs expire, so a playlist stream may eventually need
  re-resolving to play again (display of the cached title keeps
  working). Storing original links + resolve-on-play was considered and
  deferred.
- A stream URL is queue content **iff** it is keyed in `yt_info` — the
  same rule drives the queue list, playlist saving and the info box
  routing.

## Pitfalls

- Don't duplicate a layout across panes: it drifts. Extract a shared
  builder (`yt_stream_info_parts`) and route the panes through it.
- ratatui `Scrollbar::orientation()` resets the theme's scrollbar
  symbols — use `as_styled_scrollbar()` as-is (already in the handoff,
  reaffirmed by the new scrollable box).
- The scrollbar bottom pixel maps to `(height-1)*max/height`, **not**
  `max` — the reference formula the tests must assert.

## Session 2 follow-up (superseded-fetch bug)

- User hit a transient bug: navigating into "Chapter & Verse" and
  "DEADLIFE" showed an empty right pane; a reload fixed it.
  **Root cause found and fixed** (not just reload luck): `fetch_children`
  uses one `replace_id` identity, and the client task skips superseded
  queries **without firing their callback** (`should_skip_request` in
  `src/core/client.rs`). The skipped path stayed in the pane's `pending`
  set forever, so re-entering it short-circuited the fetch and rendered
  an empty pane until a Database/reload cleared the state.
- Fix: `on_query_finished` (FETCH_DATA) now clears the whole `pending`
  set — only the last fetch of the identity can ever deliver a result,
  so everything else is moot (any genuinely in-flight later fetch
  delivers its own result and clears again). Superseded dirs fetch fresh
  on re-entry.
- Tests: 1113 passing (was 1112; +1 `superseded_fetch_never_sticks_in_pending`).

## Session (2026-08-05, late) — mpv tracking across TUI restarts + full mutual exclusion

The user asked for (1) mpv playback info tracked while the TUI is
closed — reflected on reopen and reported to Jellyfin — and (2) mpv video
and MPD music to never play at the same time, either direction. The core
(reattach + tracker daemon + Jellyfin reporting) already existed; this
session closed the gaps:

- **Tracker watches MPD while the TUI is closed** (`scripts/s2u-mpv-tracker`,
  now versioned in the repo and installed by `setup.sh`; live copy at
  `~/.local/bin`). In caretaker mode it polls MPD `status` alongside mpv:
  - MPD starts playing while the video plays → pause mpv (IPC).
  - The video resumes (MPRIS controls) while MPD plays → pause MPD
    (raw MPD protocol, `pause 1`).
  - Latches arm on the first caretaker tick so pre-existing state is not
    mistaken for a fresh start; if a race left **both** playing at
    takeover the video is paused (music wins); an already-paused video is
    never touched. Pausing is one-way (no auto-resume).
  - MPD address resolution: `S2U_MPD_HOST/PORT` → `MPD_HOST/PORT` →
    `address:` in `~/.config/rmpc/config.ron` → 127.0.0.1:6600; unix
    sockets supported when the host starts with `/`.
- **Rust (`src/core/event_loop.rs`)**:
  - `MpvSessionEnded` now clears the `MPV_RUNNING` flag — a reattached
    session has no launcher thread, so it stayed `true` forever after the
    mpv exited.
  - Reattach pauses mpv when `ctx.status.state == State::Play` (restores
    the invariant if a race left both playing).
  - `MpvPoll` pauses MPD when a paused video is resumed while MPD plays
    (the TUI-open side of "video starts last → music pauses", e.g. the
    transport key driving mpv directly).
- **Tests**: `tests/tracker/test_tracker.py` — 5 scenarios against fake
  mpv + MPD servers (MPD-start pauses the video, video-resume pauses the
  music, takeover restore, paused-video untouched, state-file lifecycle
  written/deleted). All pass; `cargo test --release` still 1137.
- **Docs**: `mpv-session.md` gained a Mutual exclusion section + the
  tracker's versioning; HANDOFF gotchas/current-state updated.
