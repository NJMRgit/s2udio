# Feedback round 32 — queue startup selects the playing track at the TOP of the viewport; wheel scrolls the viewport (not the selection)

Date: 2026-08-12 · Branch: `working` · **STATUS: OPEN — for isodev.**

## Context

Two pieces of user feedback from the 2026-08-12 live-check session.

---

## 1. Queue startup behavior — select the playing track, positioned at the TOP of the visible viewport

When s2udio opens, the queue must select the currently playing track and
position that selected row at the **top** of the visible viewport — i.e.
the playing track must be the **first visible row** (scroll offset = the
playing track's index, clamped so the list never scrolls past its end).

What was wrong last time: the list scrolled down as little as possible,
which left the playing track as the **last** visible row (just barely
scrolled into view at the bottom edge). That is NOT what the user wants.
"Close to the top" refers to the selected item's position **within the
visible area** — it must sit at the very top of the screen, even if that
means scrolling a long way down a long list.

### Requirements

- On app start (first show of the Queue pane), move the highlight to the
  currently playing song **and** set the scroll offset so that song is the
  first visible row.
- This must be **one-shot**: later tab switches / re-shows must keep the
  user's current selection and scroll position.
- Use an explicit "select at top" operation (e.g. the existing
  `DirState::select_at_top` in `src/ui/dirstack/state.rs`:
  `offset = min(playing_index, content_len - viewport_len)`) — **do NOT
  reuse the generic `select()`/scrolloff path**, whose small-scrolloff
  behavior bottom-anchors the row.

### Implementation pointers (current code)

- `QueuePane::before_show` (`src/ui/panes/queue.rs`) already has the
  one-shot startup jump guarded by `startup_jump_done` — it currently
  lands the highlight with a plain `select_idx`-style move that lets the
  scrolloff path place the row at the bottom edge. Swap that path for
  `select_at_top(playing_idx)` on the first show only.
- `DirState::select_at_top` exists with tests
  (`select_at_top_scrolls_the_selection_to_the_first_row`,
  `select_at_top_handles_empty_content`) — reuse it.

### Open questions (isodev: pick sensible defaults, flag anything ambiguous)

- Does this apply only to the **audio** queue list, or also to the Video
  list's startup highlight? Default: audio list only (the feedback says
  "the currently playing track"; the video list already has its own
  startup landing).

## 2. Scroll wheel — scroll the viewport, do NOT move the selection

The wheel currently scrolls selections (moves the highlight, like w/s).
The user wants that changed in most places:

### New behavior (wheel scrolls the viewport only — it does not control the selection)

Applies to:

- **Queue** (all lists + info)
- **Playlists** (all panes/pages\*)
- **MPD** (all pages/panes)
- **Help**
- **Radio** (all panes/pages\*)

\* = "if added in future" — any new pane/page inherits the same rule.

### Explicitly NOT changed

- **Settings** — keep the current scroll wheel behavior there.

### Summary

- Old behavior = wheel scrolls selections.
- New behavior = wheel scrolls the viewport (does not control selection).

### Notes for isodev

- "Viewport scroll" means the list's scroll offset moves without changing
  the highlighted row — the selection can leave the visible area. The
  wheel must clamp at the top/bottom of the list (and at the end of an
  info box's content).
- Info boxes already scroll their content on wheel — keep that (the
  "scroll viewport" wording covers them; nothing about them changes).
- The settings panel keeps today's behavior exactly (wheel moves the
  highlighted row there).
- Lists currently implement wheel-as-selection in the panes (queue
  audio/video/chapters `video_move`/`chapters_move` wheel arms, MPD
  tree-browser, playlists, radio, help) — those wheel arms become
  viewport-scroll operations; keyboard w/s/↑/↓ and the scrollbar remain
  the selection/viewport controls as today.

### Open questions (isodev: pick sensible defaults, flag anything ambiguous)

- When the selection is off-screen after a wheel scroll, should the next
  keyboard move (w/s) scroll the selection back into view first (standard
  scrolloff behavior applies on selection moves — default: yes)?
- Modifier-wheel combos (Shift+wheel etc.): no change requested — plain
  wheel only.

## Acceptance criteria (host validates after the pull)

- Fresh start with a playing track: the audio queue opens with the
  playing track highlighted as the **first visible row** (offset =
  playing index, clamped at the end of the list). Switching away to
  another tab and back keeps the user's selection and scroll position
  (the startup jump does not repeat).
- Wheel in the Queue (Audio/Video/Chapters + info), Playlists, MPD
  (tree/items/search panes + info), Help and Radio panes scrolls the
  viewport without moving the highlight; the offset clamps at the ends.
- Settings panel wheel behavior is unchanged.
- `cargo test --release` green; binary warnings ≤ 3 baseline (any tests
  asserting wheel-moves-selection updated accordingly).
