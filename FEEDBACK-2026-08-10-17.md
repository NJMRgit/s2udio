# Feedback round 24 — Esc-deselect everywhere + search tab selection/hover/dual-pane parity

Date: 2026-08-10 · Branch: `working` · **STATUS: FILED for isodev** (host,
2026-08-10). Current tree: `5e58c29` (esc-fix `6056818` already in).

## Context

Two user reports from live testing of the last builds:

1. The Esc-to-deselect from `6056818` ("Esc clears first, settings on
   second press") only worked on the **Queue** tab. It must apply to
   **every** area where multi-item selection is enabled — currently the
   Queue (audio **and** video lists), Playlists, and MPD.
2. The **Search** tab is still behind the other list tabs: it needs the
   full multi-item selection (mouse marking), the hover/highlight
   reactive elements, and the dual-pane keyboard navigation every other
   browser tab already has.

## 1. Esc-deselect everywhere multi-item selection exists

**Verified state (working tree @ `5e58c29`):**

- ✅ **Queue audio list** (`src/ui/panes/queue.rs` ≈2251): clears the
  marks, `clear_mark_anchor()`, `event.consume()` — first Esc deselects,
  second Esc opens settings.
- ✅ **Playlists tab** (root playlist list + songs inside a playlist —
  both route through `src/ui/browser.rs` ≈602): same.
- ✅ **Search results** (`src/ui/panes/search/mod.rs` ≈637): same.
- ❌ **Queue video list** (`src/ui/panes/queue.rs`, `handle_video_action`
  ≈2590–2665): multi-select exists (`video_marked`, Shift+Up/Down) but
  there is **no `CommonAction::Close` arm** — Esc does not deselect.
- ❌ **MPD tab (DirectoriesPane)** (`src/ui/panes/directories.rs`,
  `handle_action` ≈1370–1384): multi-select exists (`marked`,
  Shift+Up/Down) but there is **no `CommonAction::Close` arm at all** —
  Esc does not deselect (the settings panel opens immediately).

**Change**: give the queue video list and the MPD tab the same Close
handling as the queue audio list / browser / search:

```rust
CommonAction::Close if !<marks>.is_empty() => {
    <marks>.clear();
    <anchor>.clear_mark_anchor(); // or equivalent
    event.consume(); // Esc is bound to both Close and ShowSettings
    ctx.render()?;
}
```

The keypress must be **consumed** when a selection was cleared, so the
settings panel only opens on a **second** Esc (nothing selected). When
nothing is selected Esc keeps opening settings, unchanged.

**Acceptance criteria**:

- Esc with an active multi-selection clears the marks **and does not
  open settings** in: queue audio list, queue video list, playlists
  (songs + root), MPD tab, search results.
- A second Esc (nothing selected) opens the settings panel as before.
- The shift-range re-anchor rule from `6056818` holds in the newly
  covered panes: after Esc clears the marks, the next Shift+W/S/↑/↓
  starts a fresh range from the cursor (stale anchor must not survive).
- Pane-level tests mirroring
  `playlists::tests::multi_select::esc_with_a_selection_consumes_the_keypress`
  and `shift_range_reanchors_after_esc_clears_the_selection` added for
  the queue video list and the directories pane.
- `cargo test --release` green; binary warnings ≤ 3 baseline.

## 2. Search tab — full multi-item selection + hover/highlight + dual-pane keyboard navigation

The Search results list is the only list that still misses the shared
selection/hover interaction (the interaction doc's list — queue
Audio/Video/Chapters, MPD, Playlists, Radio, Jellyfin — does not include
Search). The search-tab design doc says it matches "the same structure
as the other browsers", so this is parity work, not a redesign.

**Already there** (keep): keyboard shift-range select, toggle mark,
invert selection, Esc-clear, context menu / rate / add acting on the
marked set, plain-click single select, scrollbar.

**Missing — add to `src/ui/panes/search/mod.rs`:**

1. **Mouse multi-item selection** — the queue/MPD semantics
   (`queue.rs` ≈1505–1555, `directories.rs` ≈1181–1212):
   - **ctrl+click** toggles the clicked row's mark,
   - **alt+click** range-marks from the anchor (replacing the previous
     range),
   - **plain click** on another row drops the multi-selection, re-anchors
     and selects the row.
2. **Marked-row rendering** — marked rows render with
   `marked_item_style` in the results list (currently the list only uses
   `highlight_style`, so marked rows are visually indistinguishable from
   the plain selection).
3. **Hover/highlight reactive elements** — the row under the mouse
   renders with the hover style, using the shared
   `hovered_item(ctx.mouse_pos(), inner, offset, len, 1)` helper (the
   `directories.rs render_items` pattern); brightness ordering per
   `docs/design/Frontend/interaction.md`: selection ≈ 0.50 < hover ≈
   accent × 0.58 < marked ≈ 0.65 (marked rows keep their marked
   highlight on hover); hovering the
   keyboard-selected row switches its highlight to the hover style;
   keyboard input drops the pointer (existing global rule).
4. **Dual-pane keyboard navigation** — the two panes (left filter
   inputs / right results) must show which pane holds the keyboard
   cursor: the active pane renders its selection with the hover
   highlight even without the mouse (the Radio/Playlists focus
   convention — see `focused_pane_selection_uses_the_hover_highlight`),
   and keyboard movement between the panes stays consistent with the
   other browser tabs (Search ↔ BrowseResults phases; `a`/`←` back to
   the filters, `d`/`→`/Enter into the results — already in place, keep
   it, just make the active pane visually obvious).

**Acceptance criteria**:

- ctrl/alt/plain click tests on the search results list mirroring
  `playlists::tests::multi_select::ctrl_click_toggles_and_plain_click_clears_the_marks`
  and `alt_click_ranges_from_the_anchor`.
- Render tests: a marked row renders with `marked_item_style`; the row
  under the mouse renders with the hover style (dimmer than marked).
- A focused-pane test mirroring
  `playlists::tests::multi_select::focused_pane_selection_uses_the_hover_highlight`
  for the search tab's filter-pane / results-pane focus.
- `cargo test --release` green; binary warnings ≤ 3 baseline.
